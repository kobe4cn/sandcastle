## 怎么做

1. 先读仓库里现成的说明：README、CLAUDE.md / AGENTS.md、CONTRIBUTING、术语表、ADR 索引、测试目录的 README（事实里的 `docs`）。项目已经写下的规则，原样搬进对应章节或指向那份文件，不要自己另编。
2. 再看代码补没写下的：入口与目录职责、测试怎么组织（框架、夹具 / helper、怎么找相似用例、新增测试要登记到哪）、测试依赖哪些服务、提交前必须跑的命令（生成、排序、棘轮、lint）、生成文件（迁移、锁文件、快照、翻译表）、多人同时改容易冲突的文件、提交信息风格（`git log -n 10 --format=%B`）。
3. 控制成本：用 Grep / Glob 定位，只读需要的片段；整个过程不超过 60 次工具调用。不要跑测试、不要装依赖。
4. 用 Write 写 `.sandcastle/PROJECT.md`（只许改这一个文件）。

## PROJECT.md 的格式

只能用下面模板里的 `## ` 标题，不认识的标题会让流水线启动失败；「概况」「开发命令」「测试」「提交」必填，其余确实没有就整节删掉。模板的注释写了每节进哪些阶段、该写什么：

```markdown
{{TEMPLATE}}
```

写法要求：

- 每节会原样注入 agent 的提示词，写成「给 agent 的指令」：短、具体、可执行；给路径、命令、函数名，不写空话（「保持代码整洁」这类不要）。
- 只写本项目特有的。通用规则（先写测试、小步提交、不要猜）流水线的模板里已经有了。
- 命令用普通反引号；不要写 `!` 紧跟反引号的写法（那是提示词里执行命令的语法，会报错）。HTML 注释不进提示词，草稿里的注释写完后删掉。
- 「浏览器验收」只在你确认沙箱里能起 dev server 并登录时写（命令、端口、怎么建验收数据、怎么登录）；拿不准就不写这一节，改页面的票会留给人看。
- 「必须停下」写碰到就该交给人的红线（多租户隔离、计费、对外协议、数据迁移的不可逆操作……），没有就删掉。
- 不确定的不要编：留在下面的「需要人确认」里。
- 全文 60–120 行为宜，不超过 150 行。
