# 标签规则（Sandcastle 专用）

先看 `## Blocked by`（只认列表项里的票号）：有任何 blocker 还是 open，就**什么都不改**，直接结束。它等 blocker 合并后的下一轮再准备（拆票要及时）。

然后看评论里有没有 `{{REPREP_MARK}}`。有，说明 implementer 用完了会话还没做完，脚本把票退回来重新准备：**先按下面「实现没做完」一节处理，不按大小判断**。没有，就按「判断要不要处理」判断。结果只有四种：

1. **已经可以实现**（含刷新了指引）：给本票加 `{{L_PREPPED}}`。
2. **拆成了子票**：
   - 每张子票都加 `{{L_PICKED}}` 和 `{{L_READY_FOR_AGENT}}`，**不加** `{{L_PREPPED}}`（下一轮按上面的 blocker 规则逐张准备，第一张通常没有 open blocker，下一轮会直接确认）。
   - 父票去掉 `{{L_PICKED}}` 和 `{{L_READY_FOR_AGENT}}`，正文加 `## Split into`。
   - 别的票若被父票 block，改成被对应子票 block。
   - 拆票时新开的票（包括从父票挪出去、排在别的票后面的那部分）不能把父票写进 `## Blocked by`：父票拆完只留作容器，不会自动关闭，写了就永远卡住。要等的是哪张子票就写哪张。
   - `## Blocked by` 的每个 blocker 单独写一行列表项 `- #n`，列表项外的票号（说明段落、续行、括号里）不算。
3. **有设计决定要人拍板**：加 `{{L_STUCK}}` 和 `{{L_READY_FOR_HUMAN}}`，评论里写清楚要决定什么、有哪几个选项、你的建议。
4. **缺意图信息**：做这张票需要意图层面的信息（业务规则、领域术语、红线、某个设计的原因），而票、本提示词里注入的项目知识（PROJECT.md 的内容、设计决定等）和代码里都找不到。能从代码查到的事实不算，去查；不许猜着做下去。加 `{{L_STUCK}}` 和 `{{L_READY_FOR_HUMAN}}`，评论里写三件事：
   - 缺的是什么，具体到一个能直接回答的问题；
   - 应该写进哪份文档：PROJECT.md 的哪一节（用该文件现有的节标题，不新建节）、项目的术语表（如果有），或者 ADR；
   - 请人在 Claude Code 里运行 `/fill-project-docs` 补上，补完后去掉 `{{L_STUCK}}` 和 `{{L_READY_FOR_HUMAN}}`。

票正文列了待决定的选项（「要先决定……」「方案 A / B」「是否修订 ADR」之类），但正文和有写权限的人的评论里都没有明确写出选了哪个（例如「决定：A」）时，按结果 3 处理，列出选项和你的建议。`{{L_READY_FOR_AGENT}}` 标签只说明票可以排期，不代表待决定项已经选好，不许从标签推断。以 `<!-- sandcastle:decided -->` 开头的评论是 agent 写的，不算人的决定。这条优先于下面「可以代拍板」的判断。

遇到设计决定时先按下面「设计决定」判断。属于「可以代拍板」的，按那里的步骤留评论、改票（必要时开后续票），然后按结果 1 或 2 继续，不是 3。只有「必须停下」才是 3。要人在几个选项里拍板的是 3；文档里缺、只有人知道的意图是 4。

# 判断要不要处理

先看正文有没有没决定的选项（见上面「标签规则」）：有就是结果 3，不往下判断。

- **≤3 条验收标准、≤4 行 `Change`、已经有 `## Implementation guide`**：可以实现，除非指引写于它的 blocker 合并之前，或者留了没定的决定（「如果 #x 决定……」）。用 `grep -n` 抽查指引里两处 `file:line`；过时了、或上面任一条成立，就刷新指引（不拆）。否则结果是 1。
- **≤3 条验收标准、没有指引**：补指引，不拆。探索结果显示要改的已有文件超过 4 个时改成拆票。
- **超过 3 条验收标准，或要改的已有文件超过 4 个**：拆票，每张子票写指引。

# 偶发失败票（带 `{{L_FLAKY}}` 标签）

写指引前先查根因是不是已经修掉：同样的报错（失败摘要里的错误那一句）在已关闭的 `{{L_FLAKY}}` 票或主分支的提交里出现过（搜已关闭的票、`git log --oneline --grep` / `-S`），并且失败的分支早于那个修复提交（`git merge-base --is-ancestor <修复提交> <失败分支>` 返回 1）。

- **已经修掉**：把验收标准改成两条——①失败原因、修复它的提交和上面的判断依据写进提交信息；②不改代码（空提交），不重复跑测试。指引里写明判断依据，结果是上面的 1。
- **没修掉**：照常写指引。指引里要有一条修复前变红、修复后变绿的复现命令；跨进程 / 跨沙箱的竞争单跑复现不了，指引要写并发用例，不要求反复单跑；重复单跑总共不超过 20 分钟。
