# 自动合并要门槛加 forge 检查都通过

## 背景

原来自动合并只看门槛（typecheck、选测、一致性检查），PR 上的 GitHub CI 不作为条件。CI 常常覆盖门槛没覆盖的东西（lint、构建、别的平台、端到端测试），只看门槛时，CI 红着的 PR 也会被合进 main。#19 里维护者的意见是：用户看到 CI 红着的 PR 被自动合并，会以为是 bug。

## 决定

合并条件 = 门槛 + forge 检查。配置项 `mergeRequires: { checks, timeoutMinutes }`，默认 `{ checks: "all", timeoutMinutes: 30 }`：

- `all`：PR 上的检查全部通过才合并；`required`：只看必需检查；`none`：只看门槛，保留给 CI 本身不可靠的项目。
- PR 上没有检查时不阻塞（刚 push 完宽限 60 秒，仍为空就当作没有 CI）。
- 有检查失败或超时，不合并，留 PR（`sandcastle:pr-open`），评论列出检查名和链接。
- rebase 补救 force-push 后检查会重跑，要重新等检查再合并。
- 等检查期间放开宿主机锁，这张票不占实现的空位，但仍算「在做」：不会被再次开工，它改的文件仍被占着。
- forge 没实现 `prChecks` 时，每次运行在终端警告一次，按没有检查合并。

## 考虑过的方案

- **默认 `none`（保持旧行为，要等检查的项目自己打开）**：否决。默认值决定了大多数用户看到的行为；CI 红着被合会被当成 bug，而 CI 不可靠的项目是少数，显式设 `none` 即可。
- **等检查时占着空位**：否决。CI 可能要跑半小时，空位白等；票留在 `running` 里但不计入空位，既不会被重复开工，又不耽误调度开新票。
- **等检查时把票移出 `running`**：否决。`plan` 靠 `running` 排除候选和占文件，移出去会被重复开工、改同一个文件的票也会被排上。
- **把 CI 的内容并进门槛**：不强制。CI 覆盖了门槛没覆盖的东西时，项目可以自己把它们加进 `gate.script`，但不能代替等 CI。

## 后果

- 已开 `autoMerge` 的项目升级后默认会等 PR 上的检查，最多多等 `timeoutMinutes` 分钟才合并；想保持旧行为要显式设 `checks: "none"`。
- CI 不稳定会让更多票留 PR 等人；这时要么修 CI，要么设 `checks: "none"`。
- 没有 CI 的项目只多等 60 秒宽限期。
